# RTX 5060 8 GiB 端侧优化方案

## 目标
将当前单卡离线实验引擎逐步做成个人电脑可用的本地推理服务：安装简单、运行稳定、显存不足时可控、接口可集成，每项性能改动都以固定 A/B 验证。对照基线见同目录的 BASELINE_REPORT.md 与 current_engine_baseline.json。

## P0：基线和版本可追溯
- 用 Git 获取/关联真实仓库，记录远端、commit 和工作树差异；当前 ZIP 源码没有 .git。
- 固定依赖版本、CUDA/PyTorch/FlashInfer/Triton、模型配置和权重校验信息。
- 独立进程交替 A/B，至少 5 次；报中位数、离散度、TTFT、TPOT、吞吐、峰值显存、OOM。
- 记录空闲 GPU 显存、频率、温度、功耗；收益需高于测试波动且不损害输出正确性。
- 验收：实验可追溯并可按文档复现。

## P1：8 GiB 显存安全
- 拆分权重、CUDA Graph、FlashInfer workspace、KV Cache 和运行时余量，查明显存去向。
- 比较 KV block、图捕获 bucket、上下文、并发对显存和延迟的影响；配置显存余量和 OOM 前置错误提示。
- 先测 INT4 weight-only 的可用 kernel、吞吐、显存和质量，再评估低精度 KV Cache。torchao 文档列出 INT4 工作流，但并不保证当前引擎/SM120集成后会加速。
- 验收：桌面 GPU 进程继续占显存时可重复运行，不 OOM；明确列出各配置的上下文和并发上限。

## P2：最小本机服务
- 增加本机 HTTP API、流式输出、停止/取消、超时、健康检查、队列和错误返回。
- 首版单用户、单模型，限制队列/并发，提供模型加载状态和显存状态。
- 非 SM120、无 GPU、FlashInfer 不可用时可回退或清楚报错。
- 验收：应用可稳定调用；取消请求能释放队列与 KV 资源。

## P3：低延迟调度与性能
- 当前 batch=8 吞吐高，但输入 256 的 batch TTFT 为 65.1 ms；在线默认应偏向低延迟并动态合批。
- 测 Prefill/Decode 混合时的排队、短长请求干扰、p50/p95 TTFT/TPOT。
- 对现有 FlashInfer、连续批处理、Paged KV、CUDA Graph 和融合算子做全链路 profiling，只优化被测出的瓶颈。
- Q/K Norm+RoPE 融合此前本机 A/B 仅 batch=1 小幅获益，batch 4/8 近乎持平；保留窄形状 dispatch，不因单测收益而全面启用。
- 验收：分别公布交互、请求队列、离线批处理的端到端指标。

## P4：端侧打包与长稳
- WSL 一键安装/启动；检查 Windows 驱动映射、CUDA toolkit、GPU 能力、显存和模型路径。
- 配置文件、日志、优雅退出、启动检查和错误恢复。
- 增加固定提示集质量回归、混合负载长稳、显存压力、冷启动测试；功耗数据采集后再报告 tok/s/W。
- 验收：重启可恢复、持续运行不泄漏显存、配置错误在启动阶段暴露。

## 实施次序
1. 补 Git commit、依赖锁定和模型信息；重跑版本固定的 A/B。
2. 拆显存、做 8 GiB 压力矩阵，确定安全默认上下文/并发。
3. 增加最小流式 API 和取消能力。
4. 研究动态合批与 TTFT，再决定是否改 scheduler/kernel。
5. 完成安装、回退、质量与长稳验收。
6. 再扩展量化模型/上下文；每项均以质量、显存和端到端延迟验收。

## 结论边界
仓库历史中的 7.66× 是其兼容基线对比，不等于官方 vLLM 对比，也不能保证本机同等速度。量化是否更快取决于 GPU kernel、模型和引擎集成，必须实测。单看峰值吞吐不足以代表端侧体验。
