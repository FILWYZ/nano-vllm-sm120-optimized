# Current nano-vLLM comparison — 2026-10-20

## Conclusion

On the six fixed Qwen3-0.6B workloads measured on this RTX 5060 Laptop, the current candidate (`bd28d2e9`) delivered **89.4% of vLLM 0.32.0's geometric-mean output throughput**. vLLM 0.32.0 was faster on all six workloads; the measured per-workload gap was **5.4%–18.0%**. The current candidate used about **6.35–6.38 GiB** of total GPU memory in before/after `nvidia-smi` snapshots, while vLLM 0.32.0 showed **7.47–7.54 GiB** under the tested settings.

Against the locally runnable SM120 compatibility baseline, the current candidate achieved **8.79× geometric-mean throughput**. That baseline is based on upstream nano-vLLM with the minimum changes required to run on this SM120 environment. It is **not** an unmodified upstream run.

An earlier comparison against vLLM 0.31.0 measured the current candidate at **1.03× geometric-mean throughput**. vLLM 0.32.0 is the latest stable release listed by the [official vLLM release page](https://github.com/vllm-project/vllm/releases) on the measurement date; that release was published on 2026-10-18. The 0.31.0 result is retained as historical context and must not be presented as the latest-version comparison.

These results support a bounded conclusion: the current project is substantially faster than its locally runnable SM120 compatibility baseline on this workload matrix, while it trails the current official vLLM release by a modest but consistent amount. They do not establish parity on other models, long contexts, larger batches, online serving, or other hardware.

## Workload and method

Each engine completed three independent process runs. Engine order was rotated between rounds, and the six workload shapes were also rotated. Each engine process performed a per-shape warmup before timing the measured batch.

| Requests | Input tokens per request | Output tokens per request |
|---:|---:|---:|
| 1, 4, 8 | 64 | 32 |
| 1, 4, 8 | 256 | 32 |

The runs used BF16, seed `20261020`, temperature `0.6`, `ignore_eos=True`, maximum model length 512, maximum 8 sequences, maximum 2048 batched tokens, and GPU memory utilization 0.70. Prefix caching was disabled. Input token IDs were deterministically generated by the benchmark worker from the seed and workload shape, identically for all engines. Every measured workload returned exactly the requested number of requests and output tokens. All nine runs in each matrix passed all six shapes; no workload failures were recorded.

The comparison is engine-level. The engines use different attention kernels, cache policies, block sizes, compilation paths, and framework versions. Therefore the result describes the tested software stacks as a whole; it does not isolate the contribution of one kernel or feature. The vLLM 0.32.0 environment resolved PyTorch 2.13.0+cu132, while nano-vLLM uses PyTorch 2.14.1+cu130.

## Memory and latency measurement limits

GPU memory is reported as the larger of total device memory used immediately before and after each measured batch. Transient peaks can be missed, and these totals include other GPU users. Treat the numbers as sampled snapshots, not exact per-engine peak allocations. PyTorch allocator values for vLLM are zero because this benchmark worker runs vLLM generation in a separate `EngineCore` process; those allocator fields must not be compared to nano-VLLM's in-process allocator values.

vLLM's offline output did not provide usable per-request arrival and finish timestamps in this worker, so the report gives batch latency for all systems. The test validates fixed token counts and successful execution; it does not compare generated text quality or exact token-by-token equality.

## Direct upstream nano-vLLM status

The unmodified upstream source was pinned to `GeeeekExplorer/nano-vllm` commit `bb823b3e06983d71485a8e1f23715ebd87d98ef8`. It could not be run successfully on this machine, so there is no direct upstream throughput number. The upstream code imports `flash_attn`; installing FlashAttention 2.8.3 against the available PyTorch 2.14.1+cu130 failed while compiling against ATen headers because its build used C++17 where these headers require C++20. A prebuilt wheel URL attempted during setup returned 404. A second source build in the PyTorch 2.13.0+cu130 reference environment repeatedly coincided with WSL service failures during NVCC compilation. The compatibility baseline is therefore explicitly used as the fallback comparison, per the measurement plan.
