# M10: SM120 Q/K Norm + RoPE + Paged KV Store fusion

## Why this boundary

Qwen3 applies per-head RMSNorm to Q/K, then RoPE, then writes K/V into paged
cache. Treating only RMSNorm as a standalone exercise leaves kernel launches
and a K reread in the decode path. M10 moves the fusion boundary across the KV
store while keeping Attention itself owned by FlashInfer.

The fast path is intentionally shape-specific: SM120, Qwen3 head dimension
128, contiguous FP16/BF16/FP32 tensors, int64 positions, FP32 RoPE cache and
int32 slot mapping. Unsupported cases remain on the existing PyTorch path.

## Production dispatch

Early A/B enabled the custom kernel for both prefill and decode. The isolated
operator was 4.9–8.1x faster than the equivalent compiled Q/K Norm+RoPE chain,
but several prefill workloads regressed by up to 5.42%. Extending fusion through
KV store made all six decode cases positive in one run, but wider-batch changes
remained within sub-percent process noise across repeats.

The final policy is therefore:

| Runtime case | Backend |
|---|---|
| SM120, Qwen3 head_dim=128, decode batch=1 | fused CUDA, one warp/head |
| Prefill | PyTorch Inductor |
| Decode batch > 1 | PyTorch Inductor |
| unsupported device/shape/dtype/layout | PyTorch fallback |

This policy favors a repeatable win over broad but unstable enablement.

## Final A/B

Environment: RTX 5060 Laptop SM120, Qwen3-0.6B BF16, PyTorch 2.11.0+cu128,
FlashInfer, 16-token pages and CUDA Graph decode. Each backend ran in five
independent Python processes with alternating order; each workload contains one
warmup and two measured repeats. Values below are medians of process means.

| Requests | Input | Torch decode | SM120 decode | Change | Output change |
|---:|---:|---:|---:|---:|---:|
| 1 | 64 | 217.67 tok/s | 221.53 tok/s | +1.77% | +1.24% |
| 1 | 256 | 212.94 tok/s | 217.85 tok/s | +2.31% | +1.72% |

For batch 4/8 both configurations execute the same Inductor path; their
cross-process differences are retained in the raw data but are not attributed
to the custom kernel.

## Validation evidence

- CUDA project: 180 tests passed;
- nano-vLLM: 41 tests and 5 subtests passed;
- custom mutation schemas registered for FakeTensor/fullgraph capture;
- real CUDA Graph capture and replay passed;
- Compute Sanitizer memcheck: 0 errors;
- racecheck: 0 hazards;
- NCU and SASS confirm warp shuffle reduction and hardware reciprocal square
  root; the selected kernel contains no block barrier.

Raw local runs are generated by:

```bash
python -m benchmarks.run_qk_norm_rope_ab \
  --model /path/to/Qwen3-0.6B \
  --runs 5 \
  --output-dir benchmarks/results/qk_norm_rope_final_dispatch_ab

python -m benchmarks.summarize_qk_norm_rope_ab \
  benchmarks/results/qk_norm_rope_final_dispatch_ab \
  --output benchmarks/results/qk_norm_rope_final_dispatch_ab_summary.json
```

The public claim is limited to the hardware, model and workload above. It is
not a general comparison with official vLLM or a claim that custom CUDA always
beats Inductor.
